# Two-bot browser QA

This is the local implementation of the October 2026 Two-Bot QA Loop Playbook.
It complements unit/integration tests with finite browser acceptance gates.
The checked-in ledger is paused and has no invented environment or build pins.
The CLI never contacts GitHub, drives a browser, runs an agent, or deploys.

## First activation

1. Owner selects two browser agents and private credential delivery, two isolated
   synthetic tenants (prefer separate test copies), and a demo target if wanted.
   Record reviewed evidence for synthetic-only data, outbound mail capture,
   provider test mode, private evidence storage and tenant isolation. A staging
   name or test key alone does not establish those properties. Clerk login mail
   is provider-managed; an application SMTP sink alone does not capture it.
2. Owner confirms the environment/release decision under the flight plan.
   Set each bot's `target`, `tenant`, `identity`, `isolation_evidence` and
   `build_evidence` references in `queue.json`; never put credentials there.
   `build_evidence` describes how to observe frontend AND backend commits.
   No new public endpoint or response header is assumed. Do not mirror clinical
   messages into response headers; use sanitized UI observations.
3. Create seven labels from `labels.json` and one long-running queue issue per
   bot. Set each `queue_issue` URL. GitHub posting needs explicit authorization;
   this implementation prepares content locally. Do not enable Actions.
4. Write a source-reviewed 10-15 case pilot using the shape in
   `batch.example.json`. Replace every placeholder and pin a full deployed SHA.
   `release_pins` must name frontend and backend separately, even when equal;
   add paired Core/Scribe component names for a cross-repo gate. Results must
   observe every named pin before/after the run. At least half act, at least two cover edges, and the last two perform scoped
   cleanup and inventory. Each bot uses its prefix plus YYYYMMDD. Keep fixtures
   needed by later gates in `protected_fixtures`. Review `PILOT.md` first.
5. Run the commands below manually for both bots. Resume only when isolation
   evidence is reviewed. The CLI checks presence/consistency of references;
   an operator must verify their truth and GitHub comment authorship.
6. After two successful handoff/result cycles, select a local agent runner and
   scheduler with owner authorization. No scheduler is installed by this change.
   Use a persistent single-coordinator seat per queue; inspect all comments,
   not only bot comments. Yield if another coordinator has taken the seat.
   A machine-local file lock cannot coordinate multiple machines.

## Local commands

Run from the repository root; Python 3.11+ standard library only (macOS/Linux):

```sh
python3 qa/two-bot/loop.py validate
python3 -m unittest discover -s qa/two-bot -p 'test_*.py'
python3 qa/two-bot/loop.py resume bot-1 --note 'reviewed isolation evidence reference'
python3 qa/two-bot/loop.py handoff PILOT-B1 > /tmp/qa-handoff.md
```

After an authorized coordinator posts that file to the queue, record the actual
comment URL (replace REPO and numeric IDs). Rendering never marks a batch posted:

```sh
python3 qa/two-bot/loop.py posted PILOT-B1 --note 'https://github.com/CosmaNeura/REPO/issues/1#issuecomment-1'
python3 qa/two-bot/loop.py ack PILOT-B1 --note 'https://github.com/CosmaNeura/REPO/issues/1#issuecomment-2'
python3 qa/two-bot/loop.py record PILOT-B1 --note /tmp/qa-result.json
python3 qa/two-bot/loop.py pause bot-1 --note 'Owner: build drift; wait for aligned test release'
```

`result.example.json` is the canonical RESULT shape. A human-readable bot
comment starts `[Bot 1] RESULT | batch | X PASS / Y FAIL / Z BLOCKED`, followed
by one row per case and a private sanitized evidence reference. The coordinator
checks counts, exact case coverage, browser observations, start/end commits and component release pins,
fixture inventory, and failure issues before recording the JSON. JSON is a
normalized transcription of that comment, not evidence generated by the CLI.

`record` accepts each result once. Combine its acknowledgement with the next
rendered handoff in ONE comment. If no eligible work remains, explicitly record
idle once and stop inventing batches. Pause/resume entries must also be reflected
in the queue issue. PAUSED from either owner or coordinator stops postings,
including nudges; local ingestion of already-posted comment URLs/results
remains allowed while paused, so crash recovery never requires resuming; the latest authorized RESUMED clears it. Import those decisions
into the local ledger before every operation. Never infer resume from timeout.

After an ACK is 90 minutes old, post at most one nudge and record its actual
comment URL with `nudge BATCH --note URL`; earlier/repeated ledger updates do
nothing. The CLI does not post or determine whether a nudge is due remotely.
Check remote history before posting, and reconcile a successfully posted comment
before retrying after a crash. Stable batch IDs prevent accidental duplicate work.
If a build drifts mid-batch, pause the bot and use `cancel BATCH --note
'build drift; fixture disposition and evidence reference'`. The terminal cancelled
batch preserves handoff/ACK history and cannot be recorded as a completed run.
Create a NEW queued batch ID on the reconciled release, carrying forward the
fixture inventory, then resume. Do not edit an in-flight batch's pin.

File updates take a nonblocking OS lock and atomically replace the ledger.
Do not run from separate copies of the ledger or reclaim a live lock by age.

## Defect lifecycle and finite gates

Use the issue template: `qa:reported` -> `qa:reproduced` -> `qa:fixed` ->
`qa:verified`. Fixed means the fix is actually on both approved test copies,
with the exact build observed; a merged PR alone does not qualify.
A separate browser bot retests; the coordinator closes the issue on verification
in the same authorized GitHub operation. Never let the fixer verify itself.
Not reproducible is not proof of correct behavior: retain `qa:blocked` with an
owner and repro request. `qa:not-a-defect` needs an explanation of the expected
behavior. `qa:needs-owner` records a concrete decision and notification time.
Label operations and issue closure remain agent protocol, not CLI automation.

Gates in `PILOT.md` need an exact release, cases, sanitized browser evidence,
record IDs, final fixtures and independent verification. They are finite release
checks, not an endless case-generation target. See `BRIEFS.md` for agent roles.

## Safe operation and recovery

Only synthetic data, fake microphone/audio and owned disposable fixtures.
No real patient data, physical microphone, real payments, external mail, credential
rotation or production changes. Do not capture sign-in links, tokens, upload URLs,
transcript text or audio in logs/issues/screenshots. Scribe's existing browser
suite intentionally disables traces/screenshots/video; preserve those settings.
Use redacted, approved evidence or metadata-only observation records where raw
screenshots are unsafe. Evidence references are validated as present, not scanned
for secrets; review content before any post.

Before scheduling, use one locked wrapper per role that feeds `BRIEFS.md` on
stdin to the selected runner, has a bounded runtime and private logs, checks disk
space, and never overlaps a prior live process. Stop between runs and wait for
in-flight work before handing off. Do not enable an autonomous fixer until the
full suites are reliable. Never make automated deployment part of that wrapper.

Recovery: pause both ledgers and queue threads, stop the future scheduler between
runs, retain issues/evidence and reconcile posted comments. Revert these additive
QA files to remove the tooling. No application, database, environment or workflow
changes are required by this implementation.
