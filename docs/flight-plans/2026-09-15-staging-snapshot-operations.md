encrypted workspace, configured identity, fixed ARM reads, approved public-IP
check, foreground console and PostgreSQL I/O components. Stack on PR405 at

## Composition and identity

The adapter requires the exact capture inputs and component classes, shared
native-file/runtime owners, the same encrypted configuration area, and the
loader's actual `__main__.SourceRuntimeBinding`. Importing a second bootstrap
does not create equivalent authority. The protected loader now pins and loads
this fifteenth dependency before sealing and retains its source/code bindings.

The canonical initial identity evidence must match the reviewed input digest
and explicitly establish configured-home linkage to the exact ARM token and
authenticated same-token ARM readback, without authorizing an apply. Subsequent
checks compare the configured username, token OID, home account and exact token
hashes, not changing observation timestamps. Credentials remain in memory.

Immediately before firewall creation instructions, token lifetime is verified
for the WHOLE remaining 30-minute action/cleanup window plus 30 seconds. A
successful individual request's 240-second floor is not sufficient. The fixed
application/image/revision binding returned with database credentials must match
the plan's application binding before any dump child can start.

## Deadlines, capture and cleanup

Local source/artifact/native checks use the existing sealed alarm. CLI/session,
ARM, public-IP and console methods own their own sequential guards and receive
only the remaining time from the original absolute operation deadline. The
PostgreSQL capture similarly owns its guard; no caller nests or restarts it.

Record the pre-existing firewall baseline and require the intended rule absent
before instructions. Native encryption/mount/payload checks precede capture and
are repeated by the actual PostgreSQL callback. The payload must initially be
empty. Only the existing fixed-image, fixed-staging-target credential reader and
exclusive descriptor capture are used; no shell, arbitrary SQL or file path is
accepted. Capture is one-shot, at most 1 GiB and at most 1,200 seconds including
credential readback. The handoff must still be valid before entering capture;
artifact retention checks must not invent renewal or a second execution window.

Store the actual `BoundedChildren` instance BEFORE invoking capture. The core's
finally path cancels/reaps through that same owned handle, including on capture
failure. Cancellation has its own bounded cleanup allowance and does not depend
on unexpired source/plan/handoff evidence or working identity/network checks.

Always request human rule removal after instructions were released, even after
partial instructions, expired artifacts, cancellation failure or uncertain
creation. No helper creates/removes a firewall rule. After the human reports all
mutations terminal and removal complete, independently read back the unchanged
baseline and absence of the exact temporary rule. An uncertain result is not
success. No native Azure expiry, atomic rule ownership or crash-proof cleanup
is claimed. The existing human-managed 30-minute approval is unchanged.

## Durable result and recovery

Only after closure/readback does the adapter compare every proposed metadata
field against its own recorded capture, exact inputs and explicit false
deployment/restore/receipt flags. Publication uses a fixed leaf name, exclusive
no-follow creation relative to the verified encrypted mount descriptor, initial
0600 mode, bounded writes, fsync and final 0400 mode. Native ACL, UID, device,
inode, link count, size and leaf identity are checked; the workspace/source is
revalidated afterward. The payload archive's separate directory remains intact.

An existing metadata leaf is never overwritten. A partial publication or failed
post-check refuses success and preserves the captured data and partial evidence;
there is no automatic delete, detach, replay or retry. Metadata is explicitly NOT
reusable authorization and does not claim isolated restore, migrations or release.
Recovery before live use is to stop using this dormant component. During a future
human run, complete the exact already-reviewed firewall removal procedure, retain
the encrypted artifacts and investigate only that run's identified resources.
