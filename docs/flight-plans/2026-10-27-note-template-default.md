# Account default for new Scribe notes

Tier 2 because this crosses the existing scoped note boundary. The new table
contains only provider/template IDs and a revision; no patient, transcript, note
text, authentication, consent or capture-state schema changes are included.
This change follows the section-editor/custom-template PR and precedes the
Scribe display-preference consumer.

Core owns the preference. Settings offers an explicit default or “Choose each
time.” Saving uses the normalized current doctor, validates an owned nondeleted
template, locks that doctor, and compares the preference revision. An identical
retry returns the current receipt. A competing change returns 409; the UI keeps
the user's choice until explicit discard/reload. A lost response freezes that
choice and checks the same request. No local-storage substitute is used.

The separate read-only `capture-notes` action `template_preference` preserves the
existing `templates` response. Its closed receipt is
`{session_id, default_schema_ref}` with a nullable template reference. It follows
the existing exact-session, workspace/binding, ownership and current-consent
checks; it cannot prepare, modify or save a note. Scribe validates the reference
against the current template catalogue, preselects it only when starting a new
note, and still waits for the user's normal Open note action. Retained drafts,
uncertain operations and successors retain their original template and text.

## Rehearsal and recovery

The revision was generated by the repository's Alembic autogenerate recipe,
not a manually chosen ID. An isolated local PostgreSQL schema rehearsed expand,
one synthetic preference write, local-only downgrade, and expand again. The
existing template fields remained byte-identical; the owned schema was removed.
The migration graph and focused owner/concurrency/consent/UI checks are recorded
with exact source and commands in the review packet.

Operational recovery reverts the new Scribe display preference and/or Core
receiver/UI while leaving the additive table dormant. Do not run the local test
downgrade as immediate deployed rollback. Clearing a default through Settings is
also an explicit supported action. Existing templates, drafts and saved notes
are never rewritten or deleted by changing a preference. Any later table removal
requires a separate approved contract-cleanup change.
