## Authorization, source and input binding

The actual approved invocation and independently reviewed exact plan supply
execution authority. A local approval JSON, hash, success file or callback does
not authenticate itself. The plan binds the preserved same-conversation founder
selection and prior scoped build delegation, accepted rehearsal, public config
and its actual staging-vault read evidence. Its SHA is a required CLI argument.
Use isolated Python with site loading disabled. No implicit default plan.

Before importing any repository helper, the launcher checks the entire seven-file
module closure, including itself, through retained read-only file descriptors,
ownership/mode/link checks, exact hashes and before/after path identity. Imports
execute those verified bytes, not another search-path copy. Existing helpers
must be absent from sys.modules. The source adapter's closed module inventory
includes this launcher so GitHub's exact reviewed/merged controller proof covers
all seven modules; no allowlist monkeypatch or altered snapshot consumer.

The existing authenticated Git/GitHub transport verifies the configured founder
account, normally merged PR, accepted exact Cursor review object and configured
Cursor app check, required statuses, current protected master, unchanged branch
protections/ActionsOFF and candidate ancestry/schema. It exports the candidate
using Git. Plan-supplied identity or tar hashes cannot substitute for those reads.
The four rehearsal migration hashes must occur in the actual candidate archive.

Only the same ten public frontend fields used by the existing release workflow
enter the build. The four public provider fields were read from their existing
staging 1Password vault references, with values excluded from chat/evidence logs;
the preserved read record binds their hashes to the public configuration. This
source observation is external evidence accepted by the exact plan review, not
an assertion that the local JSON proves which vault was queried. Authority stays
off. No private provider, registry or Azure credential enters build arguments,
the build HOME, Docker configuration or source context.

## Timing and execution

Plans last at most two hours. Before helper import/execution the entire selected
build budget plus ten minutes must remain, leaving room for authenticated source
checks and final acceptance. The executor's existing hard limit is one hour;
its native process-group ownership, clock-change guard and cleanup bounds remain.
The assistant runs it directly; there is no timed Terminal handoff to the user.

Fresh authenticated source/protection/account observations and all local input
bindings are checked at executor command boundaries. A new reader owns each
observation; the initial reader's short deadline is never silently extended.
Source changes, altered inputs, expiry, a changed engine/socket, or a collision
stop the attempt. During a long native build, its original executor timer owns
the process; checks run again when the command returns, before acceptance.

The launcher creates exactly one new private attempt directory below/private/tmp;
an existing path refuses. The original executor creates its random nested build
directory, uses the pinned native Nixpacks/Docker/buildx and owned Colima engine,
builds linux/amd64 frontend/backend, extracts only its stopped owned container,
and produces one immutable image archive. Logs/source/images remain on failure.

Successful return from the executor is mandatory. A build-failure.json refuses
acceptance even when a partial image or success metadata exists. The launcher
rehashes the final archive and records source/config/module/plan identities,
actual actor and returned image identity. Its result always leaves publication
and deployment authorization false. A failed evidence write also fails the call;
missing or partial evidence must never be accepted as a completed build.

--check-only checks local bindings without importing helpers, authenticating live
source, creating a directory or starting a build. It is not a live build preflight
or permission to execute. No retry, image deletion, prune, daemon restart or
rebuild under the same attempt is included. Failure diagnosis preserves the first
result and all partial artifacts; recovery requires a concrete disposition.
