# Held medication fidelity — Tier 2 private proposal

Temporary holds require a distinct status. No existing stopped/active row is automatically converted, confirmed, or re-extracted. Confirmed medication rows remain patient-wide; unconfirmed suggestions remain actionable only for the open source visit, with prior visits read-only and dated.

## Release sequence

1. Apply generated additive revision 312b217ebba4 after D4. Its autocommit enum expansion retains old values and data; retry is safe. No held producer is enabled by this migration.
2. Release held-capable ORM/API/UI readers to every Core API, worker and scheduler plus generated client. The reader source keeps create/PATCH inputs active/stopped-only and preserves extraction's old active/stopped classification. The updated medication pane declares `X-Cosmaneura-Medication-Reader: held-v1` on every medication request. This is a representation capability, not authorization. Complete all reader rollout and source-bound schema/contract checks before advancing.
3. Only after confirming the entire reader deployment release the writer source: literal held extraction and explicit owner status edits/hold/resume. Confirming a suggestion is a separate provider action. Unknown extraction statuses are omitted, never silently classified active. Per-appointment extraction idempotence and source dates remain unchanged.

The initial reader/writer proposal introduced no runtime flag. The separate release-control proposal below permits a current-main image containing both phases to be rolled out with new holds disabled. Native Scribe capture and provider Session Prep paths do not consume PatientMedication in the inspected source; the Core medication API/generated client do. The bounded A6/provider and Core native-Scribe source search found no PatientMedication/MedicationStatus consumer in those request/capture paths; this is source evidence, not an installed-native or external-client certification. Any additional deployed medication API consumer must accept held before writer activation. This proposal does not certify a live model or external integration.

## Recovery

Retain the expanded enum and every patient row. Before held writes, the previous app is conditionally compatible with the dormant enum. After any held row, stop writers and retain held-capable readers; deploy a reviewed forward fix rather than a closed old enum reader. Downgrade does not drop/rebuild the enum. Existing confirmations/history are not backfilled or rewritten.

This covers the list and confirmed reference panels. Owner and existing ViewAs/access checks precede this refusal. An owner-scoped `FOR UPDATE` lookup refreshes the current mutation target in the existing request session before checking its current and requested status. ## Separate held-write release control — private Tier 2 proposal

`HELD_MEDICATION_WRITES_ENABLED` uses the existing strict boolean configuration parser. Without an override it is false in production and unknown environments, true in development/test/staging. A false value refuses new held creates and nonheld-to-held transitions only after existing owner/ViewAs and held-reader checks. The locked current target is retained. Existing held reads, labels, metadata edits, confirmation, same-status edits, deletion and explicit Resume(active) keep their normal checks. Active/stopped operations remain compatible; no row or enum is coerced or backfilled.

Extraction omits a literal held result before drug lookup while disabled; it does not reinterpret it as active/stopped. Existing per-appointment idempotence remains unchanged, so activation does not automatically re-extract skipped source classifications. The browser receives the exact public control from its existing reference-resource response, hides new Hold/options when false or missing, and retains held labels, Resume and unsaved input. This declaration is not a grant or an expansion of the existing reference-toolkit cohort.

For production, first deploy the source-derived additive schema and this held-capable image to every API/worker/scheduler while the control remains false. Verify all server readers and the served browser asset before separately approving an explicit true override on all three roles through the normal production configuration authority. This proposal does not edit production Terraform or enable the flag. Staging/test/development preserve their currently enabled writer behavior. Disabling later stops new holds but retains existing held-capable readers/data; use a reviewed forward fix after held rows exist. The canonical current-master/source provenance and protected inventory are unchanged.

The separate proposal's new local checks are pending.
